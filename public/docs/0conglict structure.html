GDG Zero-Conflict Development Protocol

Official guidelines to ensure 0% merge conflicts and seamless collaboration for a team of 13 developers.

Part 1: The 5 Golden Rules of Operations

1. Three Separate Git Repositories (No Monorepo)

Never put all 13 developers in one single Github repository. You must create 3 completely isolated repositories:

  • gdg-backend-core (Only the 4 Node.js devs commit here)
  • gdg-web-frontend (Only the 5 Next.js devs commit here)
  • gdg-app-flutter (Only the 4 Flutter devs commit here)

Benefit: A Web developer's mistake can never accidentally break the Backend code.

2. The "Shared Folder" Guardian Rule

In our architecture, the shared/ folder contains global components (API Client, Buttons, Auth State). This is the #1 place where conflicts happen when two developers edit the same global button.

Rule: Assign one Senior Developer as the Guardian of the shared folder. Other developers build their own local components. If a global component needs a change, they must request the Guardian to do it.

3. Automated Pre-Commit Hooks (Husky)

Most merge conflicts occur because Dev 1 uses "Tabs" and Dev 2 uses "Spaces".

Rule: No code can be committed unless it passes through Husky and Prettier. The system will automatically format the code into a unified standard the moment a developer types git commit. Formatting conflicts will drop to zero.

4. Postman Mock Servers (Frontend First)

Frontend developers usually write bad dummy code while waiting for the Backend APIs to be finished, leading to major conflicts during integration.

Rule: Setup a Postman Mock Server on Day 1. The frontend team will point their .env file to this fake API URL and build 100% of their UI and State Management logic immediately using the exact JSON contracts defined in the Handoff files.

5. Strict Pull Request (PR) Policy

No developer is allowed to push code directly to the main branch.

Rule: Developers must work on isolated branches (e.g., feature/dev1_auth). When finished, they create a Pull Request. Code is only merged into main after another developer reviews and approves it.

Part 2: Technical Setup Guide for Team Leads

Follow these steps to initialize the Zero-Conflict tools for your repositories.

A. Setting up Pre-Commit Hooks (Next.js & Node.js)

Step 1: Install Dependencies

Run this in the root of your Web and Backend repositories:

npm install --save-dev husky lint-staged prettier

Step 2: Initialize Husky

This creates a .husky folder:

npx husky init

Step 3: Configure package.json

Add this exact configuration to tell the system to format files before committing:

{
  "scripts": {
    "prepare": "husky"
  },
  "lint-staged": {
    "**/*.{js,jsx,ts,tsx,json,md}": [
      "prettier --write"
    ]
  }
}

Step 4: Configure the Hook

Open the file .husky/pre-commit and write:

#!/usr/bin/env sh
. "$(dirname -- "$0")/_/husky.sh"

npx lint-staged

(For Flutter, use the git_hooks package with the dart format command).

B. Setting up Postman Mock Servers

Step 1: Create a Collection

Open Postman, click New > Collection. Name it GDG App APIs and share it with the team.

Step 2: Add API Requests & Examples

Add a request (e.g., GET /api/users/me/stats). Click the Three Dots (...) > Add Example. Paste the exact JSON response from our Handoff documents and save it.

Step 3: Generate the Mock Server

On the left sidebar, click Mock Servers > Create Mock Server. Select your collection. Postman will generate a public URL like https://b48a2-mock.pstmn.io.

Step 4: Connect the Frontend

Tell Web and App developers to set this URL as their API_BASE_URL. They can now build the entire app using this mock data without waiting for the backend!
