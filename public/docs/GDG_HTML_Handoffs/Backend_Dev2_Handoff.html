Technical Specification & Handoff: Backend Developer 2 (Core Business)

Developer Profile: Backend Dev 2
Working Directory: backend/src/dev2_core_business/
Core Responsibilities: Tasks/Works Management, Dynamic Forms, Leave Applications, and Central Repository.

Objective: This document provides the complete business logic, API contracts, and database specifications required to build your module. You are responsible for writing the actual implementation code (Node.js/Express). All edge cases, inputs, and outputs are defined below so you can work entirely independently without needing to consult the rest of the team.

1. Global Naming & Data Dictionary (Must Follow)

To ensure your APIs connect perfectly with the Web and App teams, you MUST strictly use these exact terms in your Database schemas and API JSON responses:

  • Identifiers: Always use userId, taskId, formId. NEVER use user_id, task_id, or id_task.
  • JSON Keys: Always use camelCase (e.g., assignedTo, dueDate, documentUrl).
  • Response Format: Every single API response you build MUST be wrapped in this exact format:
    • Success: { "success": true, "data": { ...your_data } }
    • Error: { "success": false, "message": "error string" }
  • Enums: Status strings must be strictly lowercase: "pending", "in-progress", "completed". Do not capitalize them in the backend.

2. Database Schema Specifications

You are responsible for creating multiple Mongoose models.

A. Task Collection (TaskModel.js)

  • title: String, Required.
  • description: String.
  • assignedTo: ObjectId, Reference to User collection.
  • createdBy: ObjectId, Reference to User collection.
  • status: String enum ('pending', 'in-progress', 'completed', 'cancelled'), Default: 'pending'.
  • priority: String enum ('low', 'medium', 'high', 'urgent'), Default: 'medium'.
  • dueDate: Date (ISO 8601).

B. Form & FormSubmission Collections (FormModel.js, FormSubmissionModel.js)

  • Form:
    • title: String.
    • description: String.
    • fields: Array of objects (e.g., [{ fieldName: "Email", type: "text", required: true }]).
    • createdBy: ObjectId.
    • isActive: Boolean.
  • FormSubmission:
    • formId: ObjectId (Reference to Form).
    • userId: ObjectId (Submitter).
    • responses: Map / Object (e.g., { "Email": "test@test.com" }).

C. LeaveApplication Collection (LeaveModel.js)

  • userId: ObjectId.
  • reason: String.
  • startDate: Date.
  • endDate: Date.
  • status: String enum ('pending', 'approved', 'rejected'), Default: 'pending'.
  • reviewedBy: ObjectId (Reference to User who approved/rejected it).

3. API Contracts & Business Logic

A. Tasks Module (/api/tasks)

1. Create a Task (API-08)

  • Endpoint: POST /api/tasks
  • Auth Required: Yes (JWT)
  • Request Payload: { "title": "string", "description": "string", "assignedTo": "objectId", "dueDate": "iso_date", "priority": "high" }
  • Business Logic Flow:
    1. Extract createdBy from req.user.userId.
    2. Save task to DB.
    3. Cross-Team Integration: Call NotificationService.trigger(assignedTo, "New Task", title, "task") (This service is built by Dev 1).
  • Success Response (201): Newly created task object.

2. Get Tasks (API-09)

  • Endpoint: GET /api/tasks
  • Query Params: ?page=1&limit=20&status=pending&assignedTo=123
  • Business Logic Flow:
    1. Build query based on filters.
    2. Return paginated tasks.
    3. CRITICAL: Use .populate('assignedTo', 'name profilePicture') so the frontend can display the assignee's face and name without making a second API call.

3. Update Task Status (API-10)

  • Endpoint: PATCH /api/tasks/:taskId/status
  • Request Payload: { "status": "completed" }
  • Business Logic Flow:
    1. Update status.
    2. Trigger notification back to the createdBy user that the task was completed.

B. Forms Module (/api/forms)

  • API-13 Logic:
    • Provide POST /api/forms for admins to create dynamic schemas.
    • Provide POST /api/forms/:formId/submit for users to submit data. The controller must loop through the Form.fields definition and ensure the user submitted all required: true fields.

C. Leaves Module (/api/leaves)

  • API-14 Logic:
    • Users can POST /api/leaves to apply.
    • Admins can PATCH /api/leaves/:leaveId to approve/reject.
    • Ensure an approval triggers a notification to the applicant.
