Technical Specification & Handoff: Backend Developer 1 (Auth & Users)

Developer Profile: Backend Dev 1
Working Directory: backend/src/dev1_auth_users/
Core Responsibilities: Authentication System, User Profiles, Member Directory, and Notification Service architecture.

Objective: This document provides the complete business logic, API contracts, and database specifications required to build your module. You are responsible for writing the actual implementation code (Node.js/Express). All edge cases, inputs, and outputs are defined below so you can work entirely independently without needing to consult the rest of the team.

1. Global Naming & Data Dictionary (Must Follow)

To ensure your APIs connect perfectly with the Web, App, and other Backend developers without anyone having to ask questions, you MUST strictly use these exact terms in your Database schemas and API JSON responses:

  • Identifiers: Always use userId, roleId. NEVER use user_id, uid, id_user, or role_id.
  • JSON Keys: Always use camelCase (e.g., profilePicture, socialLinks, onboardingComplete).
  • Response Format: Every single API response you build MUST be wrapped in this exact format:
    • Success: { "success": true, "data": { ...your_data } }
    • Error: { "success": false, "message": "error string" }
  • Enums: Status strings must be strictly lowercase: "active", "inactive", "suspended". Do not capitalize them in the backend.

2. Database Schema Specifications

You are responsible for creating the User Mongoose model. Ensure your schema strictly follows these requirements:

User Collection Fields:

  • name: String, Required.
  • email: String, Required, Unique, Lowercase.
  • passwordHash: String. Security Rule: Must be excluded from standard queries by default (use select: false in Mongoose) to prevent accidental data leaks.
  • googleId: String, Sparse index. (For users who sign up via Google).
  • roleId: ObjectId, Required. Reference to the Role collection (which will be built by Dev 4).
  • profilePicture: String (Will store Cloudinary URLs). Default: Empty string.
  • bio: String, Max length 500 characters. Default: Empty string.
  • skills: Array of Strings.
  • socialLinks: Object containing github (String) and linkedin (String).
  • onboardingComplete: Boolean, Default: false.
  • status: String enum ('active', 'inactive', 'suspended'), Default: 'active'.
  • lastLogin: Date, Default: Current date.

2. API Contracts & Business Logic

A. Authentication Module (/api/auth)

1. Register User (API-01)

  • Endpoint: POST /api/auth/register
  • Auth Required: No
  • Request Payload: { "name": "string", "email": "string", "password": "string" }
  • Business Logic Flow:
    1. Validate input fields.
    2. Check if the email already exists. If yes, return 409 Conflict.
    3. Hash the password using bcrypt (Salt rounds: 10).
    4. Save the user to the database. Assign a default roleId (e.g., standard member).
    5. Generate a JWT token valid for 7 days. Payload must include { userId, roleId }.
  • Success Response (201): { "success": true, "token": "...", "data": { ...user_object_without_password } }

2. User Login (API-04)

  • Endpoint: POST /api/auth/login
  • Auth Required: No
  • Request Payload: { "email": "string", "password": "string" } OR { "googleToken": "string" }
  • Business Logic Flow (Email/Pass):
    1. Fetch user by email. Important: You must explicitly select passwordHash in your query to compare it.
    2. Compare passwords using bcrypt. If mismatch, return 401 Unauthorized.
    3. Update lastLogin timestamp.
    4. Generate and return JWT.
  • Business Logic Flow (Google OAuth):
    1. Verify the Google token using google-auth-library.
    2. Extract email. If user exists, log them in. If not, auto-register them without a password and log them in.

B. User Profile Module (/api/users)

1. Complete Onboarding (API-02)

  • Endpoint: POST /api/users/onboarding
  • Auth Required: Yes (Requires JWT)
  • Request Payload: { "bio": "string", "skills": ["string"], "socialLinks": { "github": "string" } }
  • Business Logic Flow:
    1. Extract userId from the decoded JWT.
    2. Update the user's document with the provided fields.
    3. Set onboardingComplete to true.
  • Success Response (200): Updated user object.

2. Member Directory (API-03)

  • Endpoint: GET /api/users/directory
  • Auth Required: Yes (Requires JWT)
  • Query Parameters: ?page=1&limit=20&search=john
  • Business Logic Flow:
    1. Implement pagination using skip and limit.
    2. If search query is provided, perform a case-insensitive regex search on the name field.
    3. Security Rule: You MUST project/select ONLY public fields (name, profilePicture, skills, bio, socialLinks). Do not return emails, status, or system IDs to the public directory.
  • Success Response (200): { "success": true, "data": [...], "meta": { "total": 100, "page": 1, "totalPages": 5 } }

3. Get / Update My Profile (API-05, API-06)

  • Endpoints: GET /api/users/me and PUT /api/users/me
  • Auth Required: Yes
  • Note on File Uploads: For the PUT request, if a user updates their profile picture, the Web Frontend team will handle uploading the image to Cloudinary. Your API will simply receive the final Cloudinary Image URL string in the JSON payload. Do not write Multer/file upload logic here.

3. Cross-Team Integration Points (Crucial)

As part of the backend, your module will interact with systems built by other developers. Follow these strict rules to avoid merge conflicts and bugs:

1. Notifications (Interacting with Dev 3 & Dev 4)

You are responsible for writing a NotificationService class. Other developers (like the Tasks Dev or Meetings Dev) will import your class to send alerts.

  • What you must build: A reusable function/class triggerNotification(userId, title, message, type).
  • Inside this function, you must do two things:
    1. Database Save: Insert a record into the Notification collection. (Note: Dev 4 will create the Notification Mongoose Schema, you just need to insert into it).
    2. Real-time Alert: Emit a WebSocket event. Dev 3 will set up Socket.io and attach it to the global object. You will trigger it like this: global.io.to(userId).emit('new_notification', payload).

2. Authorization / Roles (Interacting with Dev 4)

  • You are responsible for generating the JWT in the Auth Controller.
  • You do not need to write the middleware that checks if a user is an "Admin" or "Manager". Dev 4 is responsible for building the RBAC (Role-Based Access Control) middleware.
  • Your only job is to ensure that roleId is included inside the JWT payload when you generate it. Dev 4's middleware will read that roleId later.
