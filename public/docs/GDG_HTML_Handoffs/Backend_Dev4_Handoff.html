Technical Specification & Handoff: Backend Developer 4 (Admin, IAM, Meetings)

Developer Profile: Backend Dev 4
Working Directory: backend/src/dev4_admin_meetings/
Core Responsibilities: Role-Based Access Control (RBAC), Global Security Middlewares, Meeting Scheduling, Attendance, and Core Shared Data Models.

Objective: This document provides the complete business logic, API contracts, and database specifications required to build your module. You are responsible for writing the actual implementation code (Node.js/Express).

1. Global Naming & Data Dictionary (Must Follow)

To ensure your APIs connect perfectly with the Web and App teams, you MUST strictly use these exact terms in your Database schemas and API JSON responses:

  • Identifiers: Always use userId, roleId, meetingId. NEVER use user_id, role_id, or id_meet.
  • JSON Keys: Always use camelCase (e.g., meetingLink, startTime, roleName).
  • Response Format: Every single API response you build MUST be wrapped in this exact format:
    • Success: { "success": true, "data": { ...your_data } }
    • Error: { "success": false, "message": "error string" }
  • Enums: Status strings must be strictly lowercase: "scheduled", "present", "absent". Do not capitalize them in the backend.

2. Database Schema Specifications

You are the foundational data architect. You are responsible for creating the schemas that other backend developers rely on.

A. Core IAM Collections (RoleModel.js)

  • roleName: String, Unique (e.g., "Super Admin", "Core Team", "Member").
  • description: String.
  • permissions: Array of Strings (e.g., ['CREATE_TASK', 'DELETE_USER', 'MANAGE_MEETINGS']).

B. Core Shared Collections (NotificationModel.js, UpdatesModel.js)

  • CRITICAL: Dev 1 is writing the NotificationService that saves data, but YOU are responsible for defining the Mongoose Model.
  • Notification:
    • userId: ObjectId (Receiver).
    • title: String.
    • message: String.
    • type: String (e.g., 'task', 'meeting').
    • isRead: Boolean, Default: false.

C. Meetings & Attendance (MeetingModel.js, AttendanceModel.js)

  • Meeting:
    • title, description.
    • startTime: Date (ISO 8601).
    • endTime: Date (ISO 8601).
    • meetingLink: String (Can be empty if using embedded Jitsi/LiveKit).
    • hostedBy: ObjectId (Reference to User).
    • status: String enum ('scheduled', 'ongoing', 'finished', 'cancelled'), Default: 'scheduled'.
  • Attendance:
    • meetingId: ObjectId.
    • userId: ObjectId.
    • status: String enum ('present', 'absent', 'late'), Default: 'absent'.
    • joinTime: Date.

3. RBAC Middlewares (Your Most Important Task)

You are the Security Guard of the backend. You must write Express Middlewares that OTHER developers will import to protect their routes.

Task: Write an authorizeRole middleware (middlewares/rbac.middleware.js).

  • Logic Flow:
    1. It should receive the JWT payload from Dev 1's Auth Middleware (req.user.roleId).
    2. It looks up the RoleModel in the DB and extracts the permissions array.
    3. It verifies if the user has the required permission (e.g., does the array include 'CREATE_TASK'?).
    4. If unauthorized, return 403 Forbidden: { "success": false, "message": "Insufficient permissions" }.

How Dev 2 will use your code:

const { authorizeRole } = require('../dev4_admin_meetings/middlewares/rbac.middleware');

// Dev 2 protects the Create Task route using YOUR middleware:
router.post('/tasks', authMiddleware, authorizeRole(['CREATE_TASK']), createTask);

4. API Contracts & Business Logic

A. IAM & Roles (/api/iam)

  • API-07: Build CRUD operations for roles (POST /api/iam/roles, GET /api/iam/roles).
  • Ensure these routes are strictly protected and only Super Admins can access them.

B. Meetings (/api/meetings)

  • API-11 (Create/Manage): Standard CRUD for MeetingModel.
    • Cross-Team: When a meeting is created, import and call Dev 1's NotificationService to alert all members.
  • API-12 (Attendance): Provide an endpoint (POST /api/meetings/:meetingId/attend) for users to mark themselves as present when they join the call. This updates the AttendanceModel.

C. System Alerts (WS-05)

  • You will use Dev 3's global Socket.io instance (global.io) to broadcast system-wide alerts to everyone.
  • Logic: global.io.emit('system_alert', { message: 'Server going down for maintenance' });

5. Cross-Team Integration Points (Crucial Summary)

Because you build the core security and shared models, every developer depends on you. Do not change model names or middleware signatures without notifying the team.

  1. Dev 1 Dependency on YOU: Dev 1 needs your RoleModel to assign default roles during User Registration.
  2. Dev 1 Dependency on YOU (Notifs): Dev 1 will import NotificationModel from '../dev4_admin_meetings/models/NotificationModel' to save alerts.
  3. Everyone's Dependency on YOU: Dev 1, Dev 2, and Dev 3 will all import your authorizeRole middleware to protect their API endpoints.
  4. Your Dependency on Dev 3: You must wait for Dev 3 to initialize global.io before you can emit system_alert broadcasts.
